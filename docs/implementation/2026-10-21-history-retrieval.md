# 历史正文检索（2026-10-21）

分支 `feature/history-retrieval`（基于 main 03d98ad）。目标：只写在历史正文里、没有进资料卡的信息（例如第十章“林舟左手受伤，无法握剑”），也能进入 AI 改写的背景和定稿冲突检查的证据。资料卡、作者审核、版本和任务队列机制不变；提取建议仍需作者审核，设定生效章节过滤不变。

## 1. 数据

正文仍以 `chapters.body` 为准，`chapter_versions` 仍是版本快照。迁移 `0015_passage_index` 新增两张可随时从正文重建的派生表：

| 表 | 字段 | 说明 |
|---|---|---|
| `chapter_chunks` | `id, work_id, chapter_id, chunk_index, start_offset, end_offset, text, source_hash, names_hash, policy` | 正文检索块。`UNIQUE(chapter_id, chunk_index)`；索引 `(work_id, chapter_id, chunk_index)`。 |
| `chunk_mentions` | `entry_id, chunk_id` | 块中出现的资料卡名称或别名。主键 `(entry_id, chunk_id)`；索引 `chunk_id`。 |

`conflicts` 增加长期证据列：`a_version_id, a_offset, b_version_id, b_source_hash, b_offset, b_anchor`（前后各 20 字定位）。`ai_requests` 增加整次定稿共用的补查预算：`tool_rounds / max_tool_rounds / tool_result_chars / max_tool_result_chars`。`job_chunks.rounds` 保存每个分析块已完成的补查轮次。

检索块与定稿分析的 9000 字大块（`finalizationChunks.ts`）用途不同，代码分开（`src/ai/retrieval/chunking.ts`），不混用。

## 2. 切块与索引维护

- 切块：合并相邻短段落，目标约 200–400 字；单段 ≤800 字保持完整，更长的段落只在句末切开，只有超长单句才硬切（按码点，不拆代理对）。参数在 `PASSAGE_CHUNKING`，改参数会改变 `policy` 字符串，旧索引自动视为过期。
- 偏移：全部是 JavaScript 字符串下标（UTF-16），`body.slice(start, end) === text` 恒成立；不使用 SQLite 字符偏移。
- 正文变化：触发器 `passage_body_changed` 在同一条 UPDATE 中删除该章的块和提及，过期索引不可能被当成最新数据读到。重建按章在一个事务内替换块和提及。
- 名称变化：提及用 Aho-Corasick 多模式匹配（`matcher.ts`，左最长、不重叠、大小写不敏感），名称集合哈希存进 `names_hash`；别名或名称改动后只重算提及，不重新切块。单字名称和别名不参与自动提及匹配（用户主动按名称检索时由 `resolveEntities` 精确解析，与自动识别分开）。
- 旧作品：进入作品（`work.opened`）、保存章节、资料变化时，`startPassageIndexer` 在前台空闲时每批补建 4 章，App 不在前台即停，不阻塞编辑。
- 查询时：先核对每章的正文哈希、名称哈希和切块策略；过期章节每次查询最多同步重建 6 章，其余走明确的“临时扫描”路径（只在内存里切块匹配本次查询，不写库）。命中结果最后再与权威正文逐字核对一次，不一致就重建并重查一次。

## 3. 检索接口（App 内部，不是 MCP 服务）

```ts
searchPassages(session, { entryIds?, keywords?, limit? })
readPassage(session, { ref, before?, after? })
```

调用方只能传实体、关键词、数量或临时编号。小说、写作位置、允许的章节范围和版本边界都来自 App 为当前任务创建的 `PassageSession`：

- 默认只查当前小说、叙述位置（阅读顺序）在当前章之前的正文章节；写作任务还允许本章选区附近窗口之前的正文；定稿检查继续用现有“本章关联段落”对照本章其他段落。
- 叙述位置不等于故事时间。提示词和每段摘录的标题都写明这一点，代码里不推断时间先后。
- 检索两路合并：实体提及索引 + 在允许范围内用 `instr(lower(text), ?)` 匹配关键词。评分 = 实体命中 + 关键词命中 + 与任务文本的二字词重叠；每个实体在叙述顺序里的第一次提及有加分；不按“最近出场”排序，所以很早的重要片段不会被后来的大量出场挤掉。去重、每章最多 2 段、总长度受限，最后按叙述顺序呈现（后来的“痊愈”排在更早的“受伤”之后）。
- 结果带章节、正文哈希（正文恰为该章定稿版本时也带版本 ID）、UTF-16 偏移、原文和实体 ID。搜索返回短摘录，`readPassage` 读取相邻 0–2 块补足语境，返回新的临时编号。
- 关键词：规则提取（`keywords.ts`），针对最常被后文违背的状态（伤势/身体部位、兵器、生死、关押、信物），并把每个线索扩展到相关和“恢复”词。暂不引入向量、embedding 或分词服务；`entries_fts` 不变。

## 4. 接入业务流程

改写、扩写、描写（`ai.prepareWriting`）：程序预取，不开模型工具循环。有相关实体（作者选的参考或附近正文提到的条目）时，最多 4 段、共 1200 字的历史摘录作为可选上下文（`HISTORY`，优先级低于正式资料，不是必选块，超出任务预算时会被删减），进入现有上下文计划、预览和生成流程。策略版本升为 `writing-3`。

定稿冲突检查（`previewFinalization` → 队列 → `finalizationRunner`）：

1. 每个分析块按相关实体和本块关键词预取最多 6 段、共 2400 字的历史摘录，给模型的是临时编号 `p1`、`p2`……；计划被预算删掉的摘录不能被引用。
2. 模型输出冲突时，`b.source` 可以是档案、本章关联段落或 `p` 编号；校验器只接受本任务实际发出的编号，并要求引文逐字在该摘录里。材料不足时模型可把 `certainty` 设为 `suspected`，保存为低严重度并在解释前加“（存疑）”。
3. 写入前（同一提交事务）再次核验：来源仍是本作品、阅读顺序在本章之前的正文章节，正文哈希与读取时一致（绑定了版本的还要求版本未变），引文确实在该位置。任一不符就整个检查任务标为过期，不发布结果；正文变化后不会用当前索引去解释旧引用。
4. 长期保存的是真实章节（`b_ref = chapter:{id}`）、正文哈希/版本、偏移和前后文锚点；临时编号只存在于该任务自己的状态里（用于恢复），不写进冲突记录。去重指纹用真实章节代替临时编号，与现有 `conflicts` 展示、跳转、去重兼容。S14a 把这一侧显示为“历史正文 · 第 N 章”，可跳到该章原句；该章检查后被改过时提示原句可能已变，只按引文定位。

提示词判断边界（`CONFLICT_JUDGEMENT`）：正常剧情变化、恢复过程、倒叙、对白或传闻不一定构成冲突；看到受伤要结合其后有没有恢复交代；没搜到恢复记录不等于证明从未恢复；材料不足报告疑点或检查限制。

## 5. 第二阶段：冲突检查的有限补查

只在冲突检查开启。条件：本章之前有正文可查，且服务没有被记为不支持工具（`caps.tools !== false`）。

- 协议：OpenAI Responses 用 `function` 工具、`function_call` / `function_call_output`（回放时不带 item id，因此 `store:false` 也不需要保存 reasoning 项）；Anthropic Messages 用 `tools` / `tool_use` / `tool_result`，助手轮次按原样回放（含 thinking 签名）。JSON 与 SSE 两种响应都能解析工具调用。
- 每个分析块：最多 2 轮工具交互，之后一次最终判断（`tool_choice: none`）；最多 3 次模型请求，重试也算在内（沿用账本的每块 3 次上限）。每轮最多执行 3 个调用，单个结果 ≤1500 字，每块结果合计 ≤4000 字（预览时已在上下文上限里预留）。
- 整次定稿共用：补查轮数 `min(2×块数, 8)`、结果字数 `min(4000×块数, 16000)`；请求上限 = 计划请求 + 2 次重试 + 补查轮数；输出预留也按补查轮数增加；仍受原期限约束。全部写在 `ai_requests`，恢复不会重置。
- 每轮的实际请求轮次、工具结果和会话状态（临时编号映射）在发下一次请求前写入 `job_chunks.rounds`；取消或中断后恢复，从保存的轮次继续。
- 服务以 400 拒绝 `tools` 时，同一块改发预览里已经列出的“仅预取”请求（系统提示不含工具说明），本次运行的后续块直接走这条路径。
- 预览（S07b）说明检索范围（本章之前的几章、预取几段，不读后文）和补查上限，“查看发送内容”展示的就是实际发送的计划。

## 6. 固定案例比较

`__tests__/eval/history-retrieval.eval.test.ts`（`EVAL_PRINT=1` 打印）。它不调用模型，衡量的是“检查需要的证据是否在上下文里”——证据不在，任何模型都只能漏报；有伤势无恢复交代时，模型就可能误报。

| 案例 | 有冲突 | 改动前证据可见 | 预取后 | 预取+一次补查 | 越界 |
|---|---|---|---|---|---|
| 伤势只在历史正文 | 是 | ✗ | ✓ | ✓ | 无 |
| 后文已交代恢复（需同时看到受伤与痊愈） | 否 | ✗ | ✓ | ✓ | 无 |
| 别名关联同一实体 | 是 | ✗ | ✓ | ✓ | 无 |
| 很早的重要片段（其后 14 章普通出场） | 是 | ✗ | ✓ | ✓ | 无 |
| 受伤段只用代词 | 是 | ✗ | ✓ | ✓ | 无 |
| 信物已丢失 | 是 | ✗ | ✓ | ✓ | 无 |
| 人物已去世（本章没有线索词） | 是 | ✗ | ✗ | ✓ | 无 |
| 后文与他作品不得混入 | 否 | — | ✓ | ✓ | 无 |

结论：改动前，7 个依赖历史正文的案例证据都不可见（结构性漏报 7/7，有恢复的案例没有恢复信息）；预取后 6/7 可见；加一次针对性补查后 7/7。没有案例混入后文或其他作品。规则预取的已知盲点是“本章文字里没有线索词”的状态变化（例如人物已去世），这类只能靠第二阶段补查或作者写进资料卡。真实模型的漏报/误报率需要用作者自己的服务在固定案例上跑一遍，见 §7。
