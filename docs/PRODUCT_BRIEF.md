# AI 小说创作伙伴

**产品说明文档（Product Brief）**

- **版本**：V1.0（讨论稿）
- **文档状态**：产品方向初稿
- **核心定位**：帮助小说新手将零散创意发展为可持续创作的完整故事

> 本文由 Word 版产品说明文档 V1.0（讨论稿）转换而来，文字内容与原文一致；原文的编号列表在 Word 中跨章节连续编号（如 5.3 节从 7 开始），此处每个列表均从 1 开始。

## 1. 产品概述

本产品是一款面向小说创作新手的 AI 创作伙伴。目标用户通常经常阅读小说、脑中拥有独特的设定或情节灵感，但缺乏系统的小说创作经验，难以独立完成世界观构建、人物设计、剧情规划以及环境、心理、外貌等描写。

产品不以“让 AI 全自动写完一部长篇小说”为目标，而是通过创意引导、资料研究、剧情设计、描写辅助和故事记忆，帮助用户逐步完善自己的创作。AI 提供选项、分析与文本候选，作者保留最终决定权。

### 1.1 产品愿景

让没有系统写作经验、但有故事想法的人，也能逐步把自己的创意发展成逻辑自洽、可持续推进的小说。

### 1.2 产品定位

- 面向小说新手的创作顾问，而不只是一个通用聊天机器人。
- 以作者创意为中心，通过提问、建议和可选方案逐步补全故事。
- 以可追溯的资料参考为辅助，尽可能减少没有依据的随意发挥。
- 以长期故事状态维护为基础，持续管理世界观、人物、剧情、时间线和伏笔。
- 以局部描写辅助为主要文本生成场景，不默认接管整部小说的自主创作。

## 2. 目标用户与核心问题

### 2.1 目标用户

- 经常阅读网络小说，对题材、人物或情节有自己的想法，但没有系统写作经验的人。
- 有独特世界观或关键设定，却不知道如何扩展成完整剧情的人。
- 知道场景中发生什么，但不擅长环境、心理、外貌、动作和氛围描写的人。
- 希望长期创作，但容易忘记人物状态、前文细节、设定限制和伏笔的人。

### 2.2 用户痛点

| 痛点 | 典型表现 | 产品应提供的帮助 |
| --- | --- | --- |
| 创意不完整 | 只有一个能力设定或一个精彩桥段，不知道故事怎么展开 | 循序渐进地提问、补全规则、提供多种发展方向 |
| 缺少创作方法 | 不知道如何安排冲突、转折、人物动机和章节节奏 | 解释创作选择的影响，给出可比较的方案 |
| 描写能力不足 | 知道剧情，却写不出环境、心理和外貌细节 | 基于场景上下文生成局部描写候选 |
| 参考依据不足 | 想借鉴其他作品的成功经验，但不知道如何分析 | 检索可信资料，提炼可迁移的叙事机制 |
| 长篇一致性困难 | 人物设定、时间线、能力规则和关系前后矛盾 | 维护故事档案、状态变更和一致性检查 |

## 3. 产品设计原则

1. 作者主导：AI 是创作伙伴和顾问，不擅自替作者决定重要设定或剧情。
2. 渐进式引导：面对模糊创意，先澄清关键问题，再逐步补全，不一次性倾倒冗长方案。
3. 有依据的建议：区分来源事实、分析推断与原创建议，展示可追溯来源。
4. 记忆可管理：所有重要设定变更可查看、确认、撤销和追溯。
5. 先工作流、后多 Agent：优先构建可控、可评估的任务流程，不为使用多 Agent 而使用多 Agent。
6. 创作与事实分离：AI 提出的候选内容不自动成为正式设定；正文事实、作者确认的规则和推测需要区分。

## 4. 核心功能模块

### 4.1 创意孵化与需求澄清

- 允许用户用自然语言输入零散创意、人物想法、能力设定或某个剧情片段。
- 识别创意中已确定的信息、缺失信息、潜在矛盾和可扩展点。
- 通过少量关键问题逐步澄清设定，避免一次性提出过多问题。
- 提供多个方向不同的候选方案，并解释各自适合的题材、优势、风险与剧情影响。
- 用户可以接受、拒绝、修改或暂存建议；未确认的内容不得直接写入正式故事设定。

### 4.2 世界观与设定管理

- 管理世界规则、地理地点、组织势力、历史背景、能力体系、社会制度和专有名词。
- 支持设定之间的关联、前置条件、限制和例外规则。
- 为每条设定保存状态、来源、创建时间、最近修改时间和版本记录。
- 在新增设定与现有设定冲突时，提示冲突并让作者决定如何处理。
- 支持导入用户自己的资料、读书笔记和参考材料。

### 4.3 人物与关系管理

- 维护人物身份、外貌、性格、目标、动机、能力、背景、秘密和成长弧。
- 维护人物关系及其变化，例如盟友、对手、亲属、师徒和利益关系。
- 按章节记录人物状态变化，避免用当前状态覆盖过去状态。
- 根据当前场景检索相关人物信息，为生成和审查提供上下文。
- 识别行为与既定性格或动机可能存在的矛盾，并以提示方式交由作者判断。

### 4.4 剧情规划与情节建议

- 支持故事梗概、主线、支线、卷纲、章节大纲和场景计划。
- 管理冲突、目标、阻碍、转折、悬念、伏笔与回收状态。
- 围绕作者提出的问题生成多个情节发展方案，并说明逻辑链和后续影响。
- 根据已确认设定和已发生事件检查新情节是否合理。
- 允许作者只完善局部情节，不要求一次性确定全书大纲。

### 4.5 资料研究与参考案例

- 检索合法可用的文学作品、公开资料、神话历史材料、写作教程及用户上传内容。
- 支持关键词检索、语义检索、来源元数据和相关性重排序。
- 从参考案例中分析叙事机制，如悬念、信息差、人物动机、能力限制和冲突升级。
- 把分析结果转化为适配当前小说的原创候选方案，而不是复制具体人物、情节或独特表达。
- 展示来源、相关片段或摘要，并明确区分来源事实、模型推断和原创建议。
- 对资料的版权、授权、来源可靠性和使用范围进行管理；RAG 不等于事实正确性保证。

### 4.6 局部描写辅助

- 重点支持环境描写、人物外貌、心理活动、动作细节、氛围塑造和对白优化。
- 根据场景目标、人物性格、视角、情绪和文风生成描写。
- 提供不同风格或强度的多个版本，例如简洁、细腻、压迫感、轻松等。
- 支持选中一段文本进行改写、扩写、缩写、润色或补充细节。
- 默认只修改指定范围，不擅自推进后续剧情或改变既定事实。
- 允许作者将采纳后的文本写入正文，并保留版本历史。

### 4.7 故事记忆与一致性检查

- 维护项目设定、已发生故事事实、当前创作上下文和作者创作偏好。
- 按当前章节检索相关历史章节、人物状态、时间线、规则和伏笔。
- 检查年龄、时间、地点、能力限制、人物关系、物品归属和事件顺序等冲突。
- 每次正文确认后，提取可能新增或变化的事实，生成待审核变更。
- 支持查看冲突依据、接受或拒绝变更、撤销变更和追溯历史版本。

## 5. 故事记忆模型与状态管理

### 5.1 建议的记忆层次

| 记忆类别 | 保存内容 | 推荐实现方式 |
| --- | --- | --- |
| 项目设定 | 世界规则、人物基础档案、地点、势力、能力体系 | 关系型数据表；必要时建立实体关系 |
| 故事事实 | 已发生事件、人物状态、物品归属、关系变化 | 结构化事件与状态记录，保留章节来源 |
| 当前工作记忆 | 本次生成所需场景、目标、参与人物和约束 | 工作流状态与上下文组装 |
| 创作偏好 | 文风、视角、节奏、用户明确提出的写作习惯 | 独立偏好配置，允许用户查看和修改 |
| 参考资料 | 外部资料、用户上传内容、章节片段和分析笔记 | 文档存储、全文索引、向量检索与来源元数据 |

### 5.2 设定状态建议

| 状态 | 含义 | 系统行为 |
| --- | --- | --- |
| PROPOSED | AI 提议，尚未被作者确认 | 可用于讨论，不作为正式规则 |
| CONFIRMED | 作者明确确认的设定 | 作为创作约束参与上下文组装 |
| ESTABLISHED | 正文中已明确发生或建立的事实 | 记录正文出处与生效章节 |
| CONFLICTED | 与其他规则或事实存在潜在冲突 | 标记冲突，等待作者处理 |
| RETIRED | 已废弃或被新设定替代 | 保留历史，避免旧内容无痕消失 |

说明：上述状态为产品建议的业务状态，不是任何框架内置的标准枚举。实际开发时可根据业务模型进一步细化。

### 5.3 变更审核流程

1. 用户输入新想法、修改正文或确认章节。
2. 系统提取可能新增、修改或冲突的设定与故事事实。
3. 将候选变更与当前故事档案、时间线及相关章节进行比对。
4. 生成变更提案，展示变更前后、依据、来源章节及潜在影响。
5. 作者接受、修改或拒绝提案；必要时允许批量确认。
6. 正式变更写入数据库并保留审计记录、版本和生效范围。
7. 下一次创作时，检索更新后的有效状态和相关历史事实。

## 6. 典型用户流程

### 流程 A：从一句灵感开始

1. 用户输入模糊的故事想法。
2. AI 提取已知设定与待澄清问题。
3. AI 逐步询问关键规则，并给出可选方向。
4. 用户选择或修改方案。
5. 系统将用户确认的内容保存为正式设定，未确认内容保留为候选。
6. AI 根据已有信息提出故事梗概或第一卷的可选结构。

### 流程 B：根据资料获得情节建议

1. 用户提出一个情节设计难题。
2. 系统检索相关参考资料与用户自己的创作档案。
3. AI 分析资料中的叙事机制，并标注来源和不确定性。
4. AI 生成多个适配当前故事的原创方案，解释各自影响。
5. 用户选择方案，系统将其作为待确认或已确认设定保存。

### 流程 C：生成局部描写并更新记忆

1. 用户选择场景或输入本段描写目标。
2. 系统检索场景、人物、视角、情绪和相关设定。
3. AI 生成一个或多个局部描写候选，不自动改变情节。
4. 用户选择、修改并确认文本。
5. 系统保存正文版本，提取新事实和状态变化。
6. 系统展示待审核记忆变更；用户确认后更新故事档案。
7. 一致性检查器对新增内容进行冲突检查并反馈。

## 7. MVP（最小可行产品）范围

第一版应验证核心创作闭环，不追求功能数量或高度自主化。建议范围如下：

| 优先级 | 功能 | MVP 要求 |
| --- | --- | --- |
| P0 | 小说项目与章节管理 | 创建项目、保存设定、编辑正文、查看章节列表 |
| P0 | 创意引导 | 对模糊创意提问，生成少量可比较方案 |
| P0 | 人物与世界观档案 | 可创建、编辑、确认和查看历史版本 |
| P0 | 局部描写辅助 | 环境、心理、外貌描写；改写与扩写 |
| P0 | 章节摘要与记忆更新 | 生成摘要和待确认状态变更 |
| P0 | 基础一致性检查 | 检查关键设定冲突并展示依据 |
| P1 | 参考资料检索 | 支持少量合法资料或用户上传文档的检索与引用 |
| P1 | 卷纲与章节大纲 | 从创意生成可编辑的故事结构 |
| P2 | 复杂多 Agent 协作 | 在单工作流验证有效后再考虑 |
| P2 | 长篇自动连续创作 | 非第一版目标 |

### 7.1 MVP 验收标准（建议）

- 用户能够从一句创意开始，通过几轮引导形成一份可编辑的基础设定档案。
- 用户可以生成局部描写，并明确控制修改范围。
- 正文确认后，系统能提出可查看、可接受或拒绝的记忆变更。
- 关键设定能追溯来源、状态和历史版本。
- 参考建议能区分来源内容、分析推断与原创方案。
- 遇到设定冲突时，系统能够提示而非悄悄覆盖既有信息。

## 8. 技术架构建议

考虑到项目发起人具备 Java 后端开发背景，并正在学习 Python、LangChain 与 LangGraph，建议采用分层实现。初期也可以先用单体服务验证产品，再按实际需要拆分。

| 层次 | 建议技术 | 主要职责 |
| --- | --- | --- |
| 前端 | Web 编辑器（技术选型待定） | 创作对话、设定面板、章节编辑、变更审核 |
| 业务后端 | Java + Spring Boot（可选） | 用户、项目、权限、章节 CRUD、版本管理、任务接口 |
| Agent 编排 | Python + LangGraph | 任务路由、状态流转、检索、生成、审核与恢复 |
| 模型接入 | LangChain 模型接口或直接 SDK | 模型调用、结构化输出、流式生成、工具封装 |
| 关系型数据 | PostgreSQL | 项目、章节、人物、设定、事件、变更记录 |
| 检索 | 全文检索 + 向量检索（可评估 pgvector） | 检索历史章节、参考资料和语义相关内容 |
| 状态持久化 | LangGraph Checkpointer + 业务数据库 | 保存工作流检查点与业务长期数据 |
| 文件存储 | 本地存储或对象存储（按需） | 用户上传资料、导入导出文件 |

### 8.1 关键架构原则

- 业务事实以业务数据库为准，不能把向量库当作唯一事实来源。
- LangGraph 的工作流检查点用于恢复执行状态；故事长期记忆应有独立、可查询的业务模型。
- 将确定性任务交给普通程序，例如保存章节、版本控制、权限校验和状态迁移。
- 让模型负责语义理解、创意建议、文本生成和候选事实提取，并用程序规则约束关键操作。
- 所有会改变正式故事档案的 AI 输出都应经过验证；重要变更默认需要作者确认。
- 将提示词、模型版本、检索结果和关键工作流输入输出纳入必要的调试与评估记录，同时注意用户隐私。

## 9. Agent 工作流建议

第一版可以采用一个主入口，根据任务类型进入不同的受控工作流，而不必部署多个自主 Agent。

| 工作流 | 输入 | 主要步骤 | 输出 |
| --- | --- | --- | --- |
| 创意孵化 | 用户的初始想法 | 识别信息 → 找出缺口 → 提问/给选项 | 创意摘要、待确认设定 |
| 资料研究 | 创作问题与题材 | 检索 → 重排 → 阅读来源 → 分析机制 | 带来源的分析与原创建议 |
| 情节规划 | 已确认设定、当前目标 | 检索上下文 → 生成方案 → 检查约束 | 可比较的剧情方案 |
| 描写辅助 | 场景、目标、风格 | 检索人物与场景 → 生成候选 → 校验范围 | 局部描写候选 |
| 记忆更新 | 确认后的正文或设定 | 提取变更 → 比对 → 冲突检测 → 作者审核 | 正式状态变更或待审提案 |

多 Agent 是否有必要，应以评估结果为依据。如果分工带来的质量提升不足以抵消成本、延迟和调试复杂度，就保留单 Agent 加工作流的结构。

## 10. 质量评估与风险控制

### 10.1 建议关注的指标

- 创意引导有效性：用户是否更容易明确自己的设定，是否减少反复推翻。
- 建议可用性：用户采纳、修改或拒绝各类方案的比例，以及拒绝原因。
- 描写质量：与场景目标、人物性格、叙述视角和指定风格的符合程度。
- 设定一致性：关键冲突的检出率，以及误报率。
- 记忆质量：重要事实是否被正确提取、错误信息是否被错误写入、历史状态是否可追溯。
- 资料可信度：引用是否真实、来源是否相关、分析结论是否超出来源支持范围。
- 运行成本：单次创作任务的模型调用次数、耗时、Token 消耗和失败率。

### 10.2 主要风险

| 风险 | 应对思路 |
| --- | --- |
| 模型凭空补全并被误当成事实 | 明确标注提议/确认/正文事实，重要更新需要审核 |
| 长篇记忆出现错误或过时 | 保留来源、版本、生效章节和变更历史 |
| RAG 检索不相关或来源错误 | 结合关键词与语义检索、重排序、来源校验和用户反馈 |
| AI 生成内容偏离用户意图 | 局部生成、范围约束、多方案选择、可撤销编辑 |
| 参考作品版权风险 | 控制语料来源和授权范围，强调分析通用机制而非复刻表达 |
| 多 Agent 导致成本与复杂度增加 | 先使用单一编排工作流，以评估结果决定是否拆分 |

## 11. 分阶段实施路线

| 阶段 | 目标 | 主要交付物 |
| --- | --- | --- |
| 阶段 1：原型 | 验证从创意到描写辅助的基础体验 | 项目管理、设定档案、创意引导、局部生成 |
| 阶段 2：记忆闭环 | 确保故事状态能随创作可靠更新 | 章节摘要、事件提取、待审核变更、版本记录 |
| 阶段 3：检索增强 | 让建议建立在可追溯资料和故事上下文之上 | 资料导入、索引、检索、来源展示 |
| 阶段 4：工作流与评估 | 提高复杂任务的可控性与可靠性 | LangGraph 工作流、检查点、测试集、质量指标 |
| 阶段 5：扩展协作 | 根据真实使用效果引入更多专业流程 | 剧情审查、伏笔管理、专业 Agent（按需） |

## 12. 当前待确定事项

- 首批重点题材：是否优先支持玄幻、都市、悬疑等特定网文类型，还是先保持通用。
- 参考资料来源：首版以用户上传资料和合法公开资料为主，还是计划建设专门语料库。
- 交互形式：以聊天为主，还是采用“聊天 + 设定面板 + 正文编辑器”的工作台形态。
- 部署方式：个人本地使用、云端 SaaS，还是先做个人原型。
- 模型选择与预算：需要结合中文创作质量、上下文长度、结构化输出、工具调用、成本和部署要求评估。
- 第一版的成功标准：优先验证新手能否更容易形成完整设定、完成局部描写并持续维护故事。

## 13. 总结

本产品的核心价值不是让 AI 代替作者完成小说，而是帮助缺乏写作经验的人逐步掌握创作方法，把零散创意发展成结构清晰的故事，并在长期创作中保持设定和剧情的一致性。

建议以“创意引导 + 局部描写 + 故事记忆更新”作为第一版的核心闭环；以有来源的资料研究和基础一致性检查形成差异化；在工作流可靠、质量可评估之后，再扩展更复杂的多 Agent 协作。
