# Private cover storage validation · 2026-10-18

D06 is connected from the shelf action and Work Info. System selection commits the cover immediately; metadata drafts and their D04 guard remain independent. Cancel returns without changing the reference. New covers use immutable private JPEG files keyed by opaque UUID tokens. This refines the earlier fixed `covers/{workId}.jpg` filename: replacing that file before a SQLite commit could lose the previous cover when the transaction fails.

Migration 0012 adds `works.cover_token`, `cover_assets` and `cover_cleanup`. Native code accepts opaque tokens or bounded image bytes, never a caller-provided filesystem path or URI. The only URI crossing out of native is the app-private image URI used for rendering. The source read is limited to 30 MiB; native decode preserves orientation, reduces the longest edge to at most 1200 pixels, and creates JPEG at quality 0.85 without copying EXIF. Android uses the Photo Picker contract with image-only selection; iOS uses PHPicker with one image. No photo-library permission was added.

The file is prepared before publishing its reference. SQLite publishes the new URI/token and the old token cleanup record in one transaction, then emits `work.updated`. Cancellation or failed I/O/commit preserves the previous file and reference. Failed post-commit deletion remains in a durable queue. Startup retries the queue and prunes abandoned unbound stages/private files after 24 hours. Soft delete and restore retain the image; permanent deletion queues removal with the work transaction. Existing arbitrary `cover_path` records without an ownership token are never passed to native deletion; permanent deletion of those legacy records remains blocked pending a safe migration.

Validation performed:

- Six feature tests cover system cancellation and oversize failure, failed reference transaction, commit-before-event visibility, durable deletion retry, text-cover removal, soft-delete/restore/permanent delete, token/path rejection, bounded content import, and deletion during an open picker.
- Two screen tests cover metadata draft preservation through immediate cover save/D04 discard, and shelf-source cancellation without opening Work Info.
- `source scripts/dev-env.sh && ./android/gradlew -p android :app:compileDebugKotlin --console=plain` passed with CoverStore and AppInfo registration/generated code together. This is a real native compile, not a device selection test.
- React Native iOS code generation passed; the generated `NativeCoverStoreSpec` signatures match the Objective-C++ methods. Full iOS compilation remains unavailable without an iPhone SDK.

Remaining device acceptance: iOS picker cancel/success, cloud-photo retrieval/background interruption, orientation/HEIC/GIF behavior, large-image resizing/quality and EXIF/GPS inspection, low-storage failure, and lifecycle termination while selection/processing is active. Android small-PNG selection, cancellation and restart persistence are now verified below; other cases are not implied by that result.

Backup uses the content facade `readCover(token)`, `importCover({base64,mimeType:'image/jpeg'})`, and `removeCover(token)`; embedded assets are now integrated in the additive backup/restore slice (see S15b/S15c). A restored reference must bind both token and URI in the backup transaction and recycle staged tokens on rollback.

Final stage Android integration: `source scripts/dev-env.sh && ./android/gradlew -p android :app:assembleDebug --console=plain` passed, producing the Debug APK with the document/cover/AppInfo modules registered. Logs: `/tmp/novel-e-assemble.log`, `/tmp/novel-e-assemble-final.log`. iOS code generation also passed (`/tmp/novel-e-codegen.log`). This verifies Android compile/link/package and bridge generation, not device file/image/share interaction or an iOS build.

## Android Release device acceptance · 2026-10-19

Tested on local `Pixel_10_Pro` AVD (`emulator-5554`), Android 17, 1280 × 2856, at `2067d4d` plus the settings native-version correction. Normal `assembleRelease` succeeded before and after that correction (3m21s initially; 34s / 355 tasks on rebuild). The normal Release APK was installed over the existing app without uninstalling or clearing data and ran its bundled JavaScript without Metro. See [Pixel merge acceptance](2026-10-19-pixel-merge.md) for the full session.

- Opening the system Photo Picker and cancelling preserved the prior cover state. Selecting the repository's `ic_launcher.png` successfully created and displayed a private JPEG cover.
- The source was only 192 × 192 pixels. The saved JPEG was inspected as 192 × 192 pixels / 6,232 bytes. This is a real small-image conversion check, not evidence for large-image scaling, HEIC, orientation correction or metadata stripping.
- With the image cover already set, reopening the picker and cancelling preserved it; force-stop and normal Release restart also preserved the displayed cover.
- A real `.ncpbak` export contained the JPEG attachment. Android document-picker restore created a separate work with its cover retained. Soft-deleting that restored test work to the recycle bin and restoring it retained the cover; no permanent deletion was performed.

Cloud photos, images near the 30 MiB limit, actual EXIF/GPS removal, low storage, interruption during selection/processing, 24-hour orphan cleanup, and iOS compile/link/device behavior remain unverified. No mock, Debug transport result or successful Release build is treated as those checks.
