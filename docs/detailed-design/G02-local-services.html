G02本地服务层（"后端"逻辑）

V1 没有服务器。本文定义 App 内的本地服务层：数据怎么存、每个操作调用哪个函数、函数内部做什么、触发哪些事件。各页面"数据与本地服务"一节引用的函数名都以本文为准。

适用
MVP（V1），Android / iOS 相同
依据
架构文档第 3–6 节、产品设计文档第 8–9 节。本文是两者的细化，冲突时以本文为准，并回写架构文档。
相关
G01 全局交互约定、G03 AI 调用与任务

1. 定位与分层

界面层  screens/          只负责展示和收集操作，不直接访问数据库或网络
  │  调用
服务层  features/ + ai/    本文定义的函数。读写数据库、调用模型、执行规则、发出事件
  │
数据层  data/  secure/     SQLite（业务数据）  系统安全存储（API Key）  文件（封面、导出）
  • 所有服务函数都是异步函数，成功返回结果，失败抛出 AppError（见第 8 节）。界面层捕获后按 G01 错误展示规则处理。
  • 写操作在一个数据库事务里完成。一个用户操作对应一个事务，失败整体回滚，界面不出现"做了一半"的状态。
  • 写操作完成后发出事件（第 7 节）。界面通过订阅事件刷新，而不是自己去推测哪些数据变了。
  • AI 不能直接修改正式内容。AI 任务只能调用标为 AI 可调用 的函数，这些函数只产生提议、候选或待审核记录。其余写函数只能由作者的操作触发（第 9 节）。
  • 时间统一用本地时区的 ISO 8601 字符串保存；ID 用 UUID v4 字符串；字数统一按"去掉空白字符后的字符数"计算（countChars，见第 5.13 节）。

4. 通用规则

4.1 回收站

作品、章节、档案条目删除时只写 deleted_at，所有列表默认排除。30 天后由启动流程彻底删除（第 10 节）。彻底删除作品时级联删除其卷、章节、版本、条目、关系、对话、提案、冲突、任务和封面文件。恢复章节时回到原卷中原来的位置（原位置及之后的章节顺延一位）；原卷已不存在时，放入作品的第一卷末尾。恢复作品时 updatedAt 不变，作品回到书架原来的位置。

4.2 章节版本快照

来源何时生成保留
auto 自动离开编辑器时，若正文与最近一个快照不同每章最多 50 个，超出删除最旧的自动快照
finalize 定稿定稿本章时永久
before_ai AI 插入前插入或替换 AI 文本之前每章最多 30 个，超出删除最旧的
manual 手动编辑器菜单"存为版本"永久
before_restore 恢复前恢复某个历史版本之前永久

4.3 章节状态

草稿 新建章节。定稿后变为 已定稿。已定稿的章节正文再被修改（正文与定稿版本不同）时变为 有修改未定稿；改回与定稿版本完全一致时恢复为已定稿。只有 kind = 'main'（正文）可以定稿；番外和草稿不参与记忆提取。

4.4 章节编号

正文章节按"卷顺序 → 卷内顺序"连续编号为第 1、2、3… 章，跨卷连续。番外、草稿不占编号。调整顺序后编号随之变化；档案中"自第 N 章起生效"保存的是章节 ID，显示时再换算成当前编号（chapters.numberOf(chapterId)）。比较"某章时的状态"时按章节在作品中的顺序比较，番外和草稿取它前面最近的正文章节。

4.6 正文格式

正文以纯文本保存：换行统一为 \n，一个换行分隔一段，去掉每段段首的空白（含全角空格），不保存缩进。编辑器显示时每段前加两个全角空格（见 S07）。所有字符偏移（光标、选区、evidenceOffset、findText）都以规范化后的存储正文为准。

4.5 档案状态

五种状态及流转见产品设计文档第 8 节。条目的状态取其字段的"最高"状态：任一字段有冲突 → 有冲突；否则任一字段正文已建立 → 正文已建立；否则任一字段已确认 → 已确认；全部为提议 → 提议。作者手动废弃整个条目时为已废弃。

5. 服务接口

标注说明：AI 可调用 表示 AI 任务可以调用；未标注的写函数只能由作者操作触发。"事件"列是函数成功后发出的事件。

5.1 works 作品

函数说明与规则事件
works.list({ status?, query? }) → WorkSummary[]排除已删除。按 max(lastOpenedAt, updatedAt) 倒序。query 去掉首尾空白后匹配书名、灵感和题材中文名（如"玄幻"），不区分大小写的子串匹配（LIKE 通配符 %、_ 转义后按字面匹配）；V1 没有自由标签，题材即作品的标签。chapterCount 只统计正文章节；charCount 统计全部未删除章节（含番外和草稿），与 S05 字数口径一致。—
works.create({ premise, genre?, title? }) → Workpremise 去掉首尾空白后 1–2000 字，必填。同一事务内创建默认卷"第一卷"。status = 'ongoing'，封面为文字书封。work.created
works.get(id) → Work不存在或已删除时抛出 NOT_FOUND。—
works.update(id, patch) → Work可改 title（0–30 字，空字符串存为 null）、genre、premise、styleNote（0–500 字）、plannedChapters（1–9999 或 null）、status。work.updated
works.setCover(id, { kind:'text' } | { kind:'image', sourceUri })图片复制到 App 沙盒 covers/{workId}.jpg，长边缩放到 1200px、JPEG 质量 0.85；替换时删除旧文件。work.updated
works.touch(id)进入作品时更新 lastOpenedAt。—
works.remove(id)写入 deletedAt，暂停该作品的排队任务。work.removed
works.overview(id) → Overview返回：章节数（正文）、总字数（全部未删除章节，含番外和草稿，见 S05 第 5 节）、计划章数、最近编辑的章节及其最后一段的前 60 字、待处理（未处理冲突数、待审核提案数、进行中和失败的任务）、档案计数（人物数、非人物条目数、伏笔数及未回收数）。—

5.2 volumes 卷

函数说明与规则事件
volumes.list(workId) → (Volume & { chapterCount, trashedChapterCount })[]按 order 排序。chapterCount 为卷内未删除章节数（正文、番外、草稿合计），trashedChapterCount 为回收站中仍属于该卷的章节数；两者都为 0 时该卷可删除。—
volumes.create(workId, title) → Volumetitle 1–30 字。追加到最后。chapters.changed
volumes.rename(id, title)同上。chapters.changed
volumes.reorder(workId, volumeIds[])提交卷的完整顺序；章节编号随之重新计算。chapters.changed
volumes.remove(id)只允许删除没有章节（含回收站中的章节）的卷，且作品至少保留一卷；否则抛出 VALIDATION。直接删除，不进回收站。chapters.changed

5.3 chapters 章节

函数说明与规则事件
chapters.list(workId) → { volume, chapters: ChapterListItem[] }[]每章含编号、标题、类型、状态、字数、更新时间、摘要、未处理冲突数。不含正文。—
chapters.create({ workId, volumeId, title, kind }) → Chaptertitle 1–30 字；默认标题为"第 N 章"（N 为下一个编号）。追加到所选卷末尾。chapters.changed
chapters.get(id) → Chapter含正文和 lastCursor。—
chapters.saveBody(id, body, cursor) → { charCount, state, warning: 'long' | 'too_long' | null }由编辑器在停止输入 2 秒后、离开编辑器、App 进入后台时调用。写入前按 4.6 正文格式规范化。正文与库中完全相同时只写 last_cursor，不改 updatedAt、不重算状态、不发事件。否则更新 charCount、updatedAt、作品 updatedAt，按 4.3 更新状态。warning：超过 20,000 字为 long，超过 50,000 字为 too_long（仍然保存）。chapter.saved
chapters.update(id, { title?, kind?, volumeId? })title 1–30 字。已定稿的正文章节改为番外或草稿时，抛出 VALIDATION（需先撤销定稿，见 chapters.unfinalize）。volumeId 改变时章节移到目标卷末尾，重新计算编号；volumeId 不变时位置不变。chapters.changed

chapters.applyAiText(id, { start, end, text, mode: 'insert'|'replace' })先生成 before_ai 快照，再把 [start, end) 替换为 text（insert 时 start = end = 光标）。text 按 4.6 规范化。返回新正文和新光标位置。chapter.saved
chapters.finalize(id) → { jobIds }正文为空时抛出 VALIDATION。事务内：生成 finalize 快照 → 状态改为已定稿、记录 finalizedVersionId → 取消该章已排队的旧任务 → 依次入队 summarize、extract_memory、detect_conflicts。再次定稿时，记忆提取只针对与上一次定稿版本相比有变化的段落（见 G03）。chapters.changed、jobs.changed
chapters.unfinalize(id)状态改回草稿，保留快照和已通过的记忆。chapters.changed
chapters.numberOf(id) → number | null见 4.4。—
chapters.findText(workId, terms: string[], { kinds }) → { chapterId, number, kind, title, count, firstOffset, firstLength }[]在未删除章节的正文中查找名称和别名：最长匹配优先、不重叠计数。返回每章出现次数和第一次出现的位置，按章节顺序排列。用于条目"出场章节"和跳到原文定位。—

5.4 versions 版本

函数说明与规则事件
versions.list(chapterId) → ChapterVersion[]倒序。不含正文。—
versions.get(versionId) → { version, body }—

5.5 entries 档案条目

函数说明与规则事件
entries.list(workId, { type?, states?, includeRetired? }) → EntryListItem[]默认排除已废弃和已删除。每项字段见 EntryListItem。按名称拼音排序（人物按首次出场章节排序）。—

entries.get(id, { atChapterId? }) → EntryDetail返回条目；当前有效的字段（指定 atChapterId 时返回该章时的状态，按章节顺序比较生效区间）；每个字段的状态、来源说明与出处（章节 ID、原句）；字段的待定提议；伏笔的回收状态；时间线节点 { chapterId, number, field, value, kind: 'fact'|'pending', factId?, proposalId? }；关系；出场章节（由 chapters.findText 计算）；未处理冲突；待审核提案。—
entries.create({ workId, type, name, aliases, summary, facts })作者手动创建，状态为已确认，来源 manual。name 1–30 字，同作品同类型下不可与未删除条目重名（含别名），否则抛出 DUPLICATE。entries.changed
entries.update(id, { name?, aliases?, summary?, facts? }, { conflictId? }?)字段值变化时插入新的 EntryFact（supersedesId 指向旧值），旧值保留在历史中；作者编辑后的字段状态为已确认（保留原来的生效章节）。facts 每项 { field, value, fromChapterId? }：传入的 fromChapterId 晚于当前值起点时为"分阶段"——新值自该章起生效，旧值保留并把 toChapterId 设为前一章；早于或等于时改写当前记录的起点（见 S12a）。value 为空串表示清空字段（旧值 toChapterId 封口）。从冲突处理进入 S12a 时传 conflictId，新 EntryFact 的 source = { kind: 'manual', ref: 'conflict:{conflictId}' }，历史中显示为"冲突处理"。entries.changed
entries.propose({ workId, items: AdoptItem[], source }) → { entryIds, factIds } AI 可调用批量写入状态为提议的条目或字段（AI 伙伴"暂存"），入参与 entries.adopt 相同，一个事务。重名时不新建，而是把字段作为提议挂到已有条目上。source.kind = 'partner' 时，同一事务内把对应选项状态改为 stashed（见 conversations.setOptionState）。撤销暂存使用 entries.undoAdopt(factIds)。entries.changed、messages.changed
entries.proposeFacts(entryId, facts, source) AI 可调用为已有条目添加提议字段（"让 AI 补全"）。同一字段已有未处理提议时替换旧提议。entries.changed
entries.adopt({ workId, items: AdoptItem[], source })作者在"采纳为设定"预览中确认后调用。每个 item 为新建或更新某条目；全部字段状态为已确认。一个事务。返回本次写入的 entryIds 和 factIds。source.kind = 'partner' 时，同一事务内把对应选项状态改为 adopted 并记录 entryIds、factIds。entries.changed、messages.changed
entries.undoAdopt(factIds)撤销一次采纳或暂存：删除本次新建的条目和字段，恢复被更新字段的旧值；同一事务内把对应选项改回 open。若其中任一字段之后又被修改过，抛出 CONFLICT_STATE（"这些设定之后改过，请到档案里手动调整"）。entries.changed、messages.changed
entries.confirmFact(factId, { value? }?) / entries.dismissFact(factId)采纳或丢弃单个提议字段。丢弃即删除该提议记录。采纳按 entries.update 的规则写入（supersedesId 指向当前值，沿用当前值的生效区间，未填写时为 null），状态为已确认，保留提议的 source；传 value 时使用作者修改后的值（S12c"改后采纳"，1–300 字）。entries.changed
entries.retire(id) / entries.unretire(id)整条废弃或恢复。废弃后不参与上下文和冲突检测。entries.changed
entries.remove(id)进入回收站。同时删除以它为端点的关系（恢复时一并恢复）。entries.changed
entries.history(id) → HistoryItem[]按时间倒序列出字段变化：字段、旧值、新值、来源（手动 / AI 伙伴 / 记忆审核 / AI 补全 / 冲突处理）、时间。每项为 HistoryItem { factId; field; beforeFactId; before: string | null; after: string | null; fromChapterId; toChapterId; sourceKind: SourceKind | 'conflict' | 'revert'; sourceRef; sourceChapterId: ID | null; evidence: string | null; at: ISO }：source.kind = 'manual' 且 ref 为 conflict:{冲突 ID} 时归为 conflict，ref 为 revert:{factId} 时归为 revert；after 为 null 表示该字段在此失效（retire）；sourceChapterId / evidence 为审核通过时的来源章节与原句（与 entries.get 的出处相同），其他来源为 null。见 S12d。—
entries.revertFact(factId)把某字段恢复为历史上的某个值（生成新的 EntryFact）：值取自 factId，作用于 factId 生效起点所在章节此刻有效的那条记录（fromChapterId 为 null 时取设定层面的记录）：新记录沿用它的 fromChapterId / toChapterId，supersedesId 指向它，state = CONFIRMED，source = { kind: 'manual', ref: 'revert:{factId}' }。值与该记录相同时抛出 CONFLICT_STATE；条目已删除时抛出 NOT_FOUND。entries.changed
entries.search(workId, query) → EntryListItem[]FTS5 trigram 匹配名称、别名、摘要和字段值；查询少于 3 个字时退回 LIKE 子串匹配。—
entries.findMentions(workId, text) → { entryId, name, count }[]在文本中查找条目名称和别名（最长匹配优先），用于描写助手"参考"和上下文组装。—

6. 后台任务队列

  1. 来源：只有 chapters.finalize 和 conflicts.recheck 会入队。
  2. 顺序：全局串行，同一时刻只运行一个任务；同一章的三个任务按 summarize → extract_memory → detect_conflicts 顺序执行，前一个失败时后面的保持 queued 并显示"等待前一步"。
  3. 使用的模型：入队时的默认模型服务。执行时若该服务已被删除，改用当前默认服务；没有任何服务时任务进入 paused，原因"未连接模型"。
  4. 暂停原因（Job.pauseReason）：no_service 没有模型服务；no_key 默认服务缺少 Key（hasKey = false，或读取 Key 时抛出 KEY_UNAVAILABLE）；notice 服务域名未确认 D01 数据说明（G03 调用管道第 3 步）；offline 系统报告无网络。自动恢复：收到 services.changed 时把 no_service、no_key 的任务改回 queued；网络恢复时把 offline 的任务改回 queued；notice 只能由作者在 S05b 点"继续"并确认 D01 后调用 jobs.resume。暂停不计入 attempts。
  5. 重试：可自动重试的错误（限流、服务繁忙、网络中断）按 G03 的退避规则最多自动重试 2 次；仍失败则为 failed，等作者在 S05b 后台任务中手动重试。Key 无效、额度不足、模型不存在不自动重试。
  6. 前后台：App 进入后台时，正在运行的请求中止，任务回到 queued；回到前台后继续。V1 不使用系统后台执行。
  7. 启动恢复：App 启动时把所有 running 改回 queued，然后开始执行。
  8. 取消与覆盖：重新定稿同一章时，取消该章所有未完成的旧任务后再入队。删除章节或作品时取消相关任务。
  9. 进度：概览页显示"正在整理第 12 章（2/3）"。任务完成后，如果产生了新的待审核提案或冲突，在当前页面底部显示一次提示（见 G01 提示条）。

9. AI 写入边界

为保证"AI 写的内容默认只是提议"，代码层面做三件事：

  1. ai/ 目录下的代码只能 import 标为 AI 可调用 的函数，由 ESLint 规则 no-restricted-imports 检查。
  2. 正式写函数（entries.adopt、entries.confirmFact、proposals.accept*、chapters.applyAiText 等）只在界面事件处理函数中调用。
  3. 自动化测试：运行所有 AI 任务（使用录制的响应），断言 entry_facts 中没有新增状态为 CONFIRMED / ESTABLISHED 的记录、chapters.body 没有变化。

10. 启动流程

  1. 打开数据库，按 PRAGMA user_version 执行迁移。迁移失败时显示错误页（"数据升级失败"，提供"导出原始数据库"以便反馈），不进入 App。
  2. 彻底删除回收站中超过 30 天的内容，清理临时导出文件。
  3. 把 running 任务改回 queued，启动任务队列；把 status = streaming 的 AI 消息改为 stopped。
  4. 路由：onboardingDone = false → S01；否则 → S03 书架。V1 不自动进入上次打开的作品。
