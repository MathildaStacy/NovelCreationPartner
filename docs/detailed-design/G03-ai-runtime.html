1. 调用管道

2026-10-18 补充：G04 成本与效果 §2明确修订业务任务总尝试预算、用量账本、上下文估算与必要事实保护、默认候选数、队列恢复及可选服务路由；这些条款以 G04 为准，其余规则继续有效。连接测试/模型列表的现有严格规则保持不变。新增行为尚待实现，进度见当前交接。

除 ai.testConnection、ai.listModels（使用 S02 中尚未保存的草稿配置）和 ai.previewContext（不联网）外，所有 ai.* 函数按以下顺序执行。前 3 步在界面层的统一入口 useAiAction() 中完成，失败时不发请求：

  1. 网络：系统报告无网络时抛出 AI_NETWORK，界面按 G01 离线提示，不排队。
  2. 模型服务：modelServices.getDefault() 为 null 时抛出 NO_SERVICE，界面打开 D03 先连接模型。服务缺少 Key（例如从备份恢复后）时同样打开 D03，主按钮改为"填写 Key"并进入 S02 编辑该服务。
  3. 数据说明：服务 Base URL 的域名不在 prefs.aiNoticeAcknowledged 中时，打开 D01 AI 数据说明；作者选择继续后记录域名，再接着执行。后台任务不弹窗：域名未确认时任务进入 paused，原因"需要确认 AI 数据说明"，在 S05b 中点"继续"时弹出 D01。
  4. 读取 Key：secure.getKey(keyRef)，失败抛出 KEY_UNAVAILABLE。Key 只存在于这次请求的局部变量里。
  5. 组装：按第 5 节组装上下文，按第 6 节生成该任务的统一请求 GenerateRequest（以本节契约为准）。
  6. 发送：交给协议适配器（第 2 节），流式任务按第 3 节读取。
  7. 解析与写入：结构化任务按第 4 节解析校验；结果只通过 G02 标为"AI 可调用"的函数写入，或只返回给界面（描写候选不落库）。
  8. 记录：按第 11 节记录用量。

并发：前台请求同时最多 3 个（描写多版本）；后台任务全局串行（G02 第 6 节）。两者互不占用名额。

2. 协议适配

2.1 请求地址

由 modelServices.resolveUrl(protocol, baseUrl, kind) 计算，规则与示例见产品设计 6.3，这里重述以便实现：

  1. 去掉首尾空白和末尾的 /。
  2. 已经以端点结尾（OpenAI /responses，Anthropic /messages）时，视为完整生成地址；模型列表地址把最后一段换成 models。
  3. OpenAI：路径以 /v数字 结尾 → 追加 /responses；路径为空 → 追加 /v1/responses；其他路径视为已含版本的网关前缀 → 追加 /responses。
  4. Anthropic：路径以 /v数字 结尾 → 追加 /messages；其他情况 → 追加 /v1/messages。
  5. 模型列表：同样规则，端点换成 models（GET）。

URL 与转发边界：按 S02 校验；拒绝 URL 用户名/密码、查询、片段、控制字符及与所选协议相反的完整端点。私网 IPv4 必须解析为合法四段地址后匹配网段，不能用字符串前缀判断。MVP 所有带鉴权请求不自动跟随任何 3xx（含同源）；返回 AI_NETWORK，提示填写最终地址。必须由原生传输层在下一跳发出前阻止，不接受 JS 在 responseURL 上事后检查。不得携带 Cookie、保存 HTTP 缓存或输出原生网络调试请求头。

2.2.0 最小传输契约

interface GenerateRequest {
  system: string;
  messages: { role: 'user' | 'assistant'; content: string }[];
  maxOutputTokens: number;
  effort?: 'low' | 'medium' | 'high';
  jsonSchema?: { name: string; schema: object };
  stream: boolean;
  signal: AbortSignal;
}
type Usage = { input: number; output: number };
type StreamEvent =
  | { type: 'text'; delta: string }
  | { type: 'done'; text: string; model: string | null; usage: Usage | null;
      stop: 'end' | 'length' | 'refusal' }
  | { type: 'error'; error: AiErrorInfo }
  | { type: 'cancelled' };
interface Provider {
  generate(req: GenerateRequest): AsyncIterable<StreamEvent>;
  listModels(opts: { signal: AbortSignal }): Promise<string[]>;
}

Provider 仅处理配置快照与一次物理请求，不访问业务库、不自行重试；features → ai 负责整个逻辑请求的 deadline、重试与探测结果。网络及协议错误以 error 事件结束；调用取消以 cancelled 结束，不伪装成断网；消费者不应再收到同一错误的重复 rejection。非流式响应也通过同一 text/done 契约返回。请求期间配置/Key 取同一快照；切换默认只影响之后的新请求。Key 不进入 GenerateRequest、事件或 UI 导航参数。

3. 流式读取

默认以 RN XMLHttpRequest 的增量 responseText 接入 SSE，但必须先验证 Android/iOS 的增量交付与原生禁重定向能力。原生桥接必须阻止下一跳并支持 abort；如 XHR 无法做到，使用应用专用的最小原生 HTTP 传输（不引入模型 SDK、后端或全局网络改写），保持 2.2.0 契约。未经设备验证不能宣称安全流式完成。

  1. 按累计 responseText 的游标消费增量；原生字节实现用有状态 UTF-8 解码。支持 BOM、LF/CRLF/CR（跨 chunk 的 CR 保留待判定），按空行切帧，多行 data 用换行连接，忽略冒号注释与未知字段。正常 EOF 时按 SSE 规则丢弃未以空行结束的残帧，不能自行补成成功事件。
  2. 合法但未知的事件可跳过；已知事件 JSON 损坏、字段类型不对或两协议结构混用 → AI_PROTOCOL_MISMATCH，不静默忽略后伪装成功。注释心跳、ping、思考事件只更新活跃计时；思考文本不对 UI 输出。
  3. 解析缓冲只留未消费尾部；XHR 累积 responseText 仍可能占用内存，不能声称流式常量内存。单帧及单次累计响应设置有限上限（1 MiB / 16 MiB，以 UTF-8 字节计）；超限中止为 AI_RESPONSE_TOO_LARGE，保留已有正文，不自动重试。

  • 唯一终态：每个逻辑请求只能有一个 done/error/cancelled。完整帧终态与 abort/deadline 竞争时先进入终态者生效；终态后解除监听、清计时器、关闭连接、释放并发名额，丢弃所有迟到事件。iterator.return() 同样中止；重复 abort 幂等。done.text 是完整正文，调用方用它校验/替换，不再追加一次。
  • EOF：无协议终态且已有文字 → AI_STREAM_INTERRUPTED；无文字 → AI_NETWORK。不把 EOF、[DONE]、HTTP 200 或 Anthropic message_delta 当成功终态。OpenAI refusal 块映射 refusal，不显示为普通文本；非流式 completed 内存在 refusal 时同样优先 refusal。
  • JSON 兜底：成功 HTTP 响应 content-type 为 application/json（允许 charset）时按 2.3 校验后返回一次 text + done，caps.streaming=false；HTML/错误协议结构 → AI_PROTOCOL_MISMATCH。非 2xx 优先按错误表处理，不把 401 HTML 错判为成功或纯协议问题。SSE 即使一个 progress 全部到达也不能记 false；真实跨多次增量返回文字才记 true，其余 streaming=null（未确认）。
  • 超时：普通生成首个响应体字节 60 秒；收到首字节后从该时刻开始、每个完整事件/心跳重置 90 秒空闲期限，无完整事件则中止为 AI_STREAM_INTERRUPTED；另设每个逻辑请求 5 分钟硬期限，防止心跳无限续命，到期 AI_TIMEOUT。非流式 JSON 从首字节起按新增字节重置空闲期限。测试及列表使用第 6.1–2 节的 20 秒总期限。计时包含前后台挂起时间，恢复 active 时先检查过期再处理缓存回调。
  • 继续生成：截断/中断后只能由作者发起新逻辑请求，带已生成 assistant 文本和「接着上文继续写，不要重复已写内容」，不能自动续费式续写。本接入阶段仅实现终止语义，不实现业务继续生成 UI。

4. 结构化输出与降级

适用于需要 JSON 结果的非流式任务：采纳拆解、方案对比、条目补全、记忆提取、冲突检测。创意引导（ideate）因为要边生成边显示，使用 4.3 的"文本 + 结尾 JSON"格式。

4.1 Schema 约定

  • 每个对象都写 additionalProperties: false，所有属性都列入 required；可选值用 ["string", "null"] 表示（同时满足 OpenAI strict 与 Anthropic 的要求）。
  • 数组长度上限写在 maxItems，字符串长度不写在 Schema 里，而写在提示词里，并在本地校验时截断。
  • 本地用同一份 Schema 校验（ajv）。

4.2 三级处理

业务任务的每一次降级/格式修复重发都占用 G04 统一尝试额度，不得把下列分支与网络重试嵌套成独立循环。

  1. 原生约束：caps.jsonSchema !== false 时，按 2.2 发送 Schema 参数。
  2. 提示词约束：若返回 400 且结构化错误明确指出不支持 text.format、output_config.format 或 json_schema 参数，把 caps.jsonSchema 记为 false，去掉该参数，在系统提示末尾附上 Schema 和"只输出一个 JSON 对象，不要输出其他文字"，立即重发一次（不计入第 9 节的重试次数，但共享逻辑请求期限）。之后该服务直接走这一级。
  3. 本地容错与校验：去掉 ``` 代码围栏 → 取第一个 { 到最后一个 } → JSON.parse → Schema 校验。失败时把校验错误附在请求末尾重发一次；仍失败 → AI_FORMAT。

推理强度参数用同样方式探测：400 且结构化错误明确指出不支持 reasoning.effort 或 output_config.effort 时，记 caps.effort = false，去掉后重发一次。服务配置（地址、协议、模型）变更时清空 caps。只报 output_config 或普通 format 不能判定哪项能力不支持；不匹配时直接 AI_BAD_REQUEST。每项能力每个逻辑请求最多降级一次；未知能力省略字段，不把 ping 测试当作 jsonSchema 探测。

4.3 创意引导的输出格式

ideate 不发送 Schema 参数。系统提示要求模型先写给作者看的回复正文，然后单独一行写分隔符 <<<NCP_JSON>>>，再写一个 JSON 对象（结构见 6.3）。

  • 流式显示时只显示分隔符之前的文字；分隔符出现后停止追加显示。分隔符可能被拆在两个事件里，判断时保留缓冲区末尾 16 个字符。
  • 完成后解析分隔符之后的 JSON，按 4.2 第 3 级的容错规则处理，但不重发：解析失败或没有分隔符时，消息仍为完成状态，structured = null，界面只显示文本（S10"只有文本"状态），不报错。

5. 上下文组装

5.1 token 估算与预算

  • 估算：estimateTokens(text) = 中日韩字符数 × 1 + 其他字符数 ÷ 4，向上取整，是初始近似，不保证高于真实 token 数。按 G04 §4加入估算余量、协议开销及实际用量校准；不用于精确计费。
  • 预算：单次请求的输入（系统提示 + 上下文 + 对话）默认不超过 24,000 token，可在 S02b 高级设置中调整为 8,000–100,000。
  • 超出时：按 5.2 的优先级从低到高裁剪；第 1、2 级不裁剪。第 1、2 级本身超出预算时（例如单章正文很长），记忆提取和冲突检测按 6.10 分段执行，其他任务抛出 AI_CONTEXT_TOO_LONG。

6.1 testConnection(draft, key, { signal, onRetry? }) → TestResult

  1. 整个逻辑测试（GET 分页、生成、重试等待和参数降级）共享一次 20 秒 deadline；取消覆盖所有子请求和退避计时器。GET 模型列表成功时计算 modelCount/modelListed；仅 404 / 405 跳过，其他错误（含超时、401/403）直接失败，不继续生成。
  2. POST 最小生成：仅发送「ping」、stream=true、最大输出固定 64、effort=low（已知不支持则省略）。忽略服务自定义最大输出/强度；OpenAI 连接测试固定 store=false。只有明确不支持 effort 才去掉重发一次。不探测结构化输出、不自增 token 上限。合法 end/length/refusal 均表示协议请求已被处理，ok=true；length 无可见文本也可成功，但必须有合法终态。
  3. 仅生成阶段对无已收文字的 AI_RATE_LIMIT/AI_SERVER 最多自动重试 2 次，仍受总 deadline 限制；等待不能容纳于剩余期限时直接返回当前错误，不发新请求。合计生成 POST 最多 4 次（初次 + 2 次可重试错误 + 1 次 effort 降级），没有隐式循环。模型列表阶段不自动重试。
  4. latencyMs 为最后一次实际生成尝试从发送到终态的耗时（不含列表/等待）；未发生成时为 0。页面「已用秒数」按整个测试计时。模型不在列表不影响生成；list 不可用时 models/modelCount/modelListed=null。
interface TestResult {
  ok: boolean; at: ISO; latencyMs: number;
  modelCount: number | null; modelListed: boolean | null;
  models: string[] | null; responseModel: string | null;
  streaming: boolean | null;
  capsPatch: Partial<ModelService['options']['caps']>;
  error: AiErrorInfo | null;
}

ok=false 时 error 非空，ok=true 时 error=null；responseModel 缺失则 UI 回退所填模型。capsPatch 只包含确有证据的能力变化；streaming=null 不覆盖已保存能力。S02 的测试凭据/配置关联及 S15a 写回规则见 G02 5.11.3；本函数不直接写数据库。取消抛 AI_CANCELLED，既不写失败记录也不弹错误。

6.2 listModels(draft, key, { signal }) → string[]

  • OpenAI 读取 data[].id；Anthropic limit=1000，has_more=true 时用 last_id 作为 after_id，最多 5 页。缺必需游标或游标重复 → AI_PROTOCOL_MISMATCH；字段校验后去重、保留服务返回顺序，排序由 S02a 完成。
  • 独立列表请求所有分页共享 20 秒 deadline；在连接测试内则共享测试剩余期限。不自动重试；手填模型始终可用。校验不要求填写 model。
  • 页面内 10 分钟缓存按协议、规范化列表 URL、鉴权方式、服务 revision 和本页 Key 编辑代次标识，Key 编辑/显隐读出后的实际变更会失效；不使用 Key 原文或其哈希作为缓存键。测试返回 models 可复用，离页清除。

6.3 ideate(conversationId, assistantMessageId, { scope, mode })

  • 上下文：5.2 全部层级，范围取对话的 PartnerScope。
  • 任务要点：先用两三句话回应作者；需要作者决定的事最多问 3 个；给出 2–3 个方向明显不同的选项，每个说明适合的走向、风险和对后续的影响；作者只是闲聊或提问时可以不给选项（数组为空）。mode = more_options 时：回复正文一句话即可，给出 2–3 个与本对话中已有选项都不同的新方向。
  • JSON 结构（4.3 分隔符之后）：
{ "known":     string[]   // ≤ 6 条，每条 ≤ 40 字：从作者话里归纳出的已明确信息
  "questions": string[]   // ≤ 3 条，每条 ≤ 40 字
  "options": [ { "title": string,      // ≤ 12 字
                 "summary": string,    // ≤ 60 字
                 "direction": string,  // 适合的走向，≤ 40 字
                 "risks": string,      // ≤ 40 字
                 "impact": string } ]  // 对后续剧情的影响，≤ 40 字；0 或 2–3 个
}
  • 写入：流式文字经 conversations.appendAssistant(messageId, delta)；完成时写入 structured（每个选项补 state: 'open', entryIds: [], factIds: []）、usage、status。超长字段截断，超出数量的取前几个。

6.4 compareOptions(messageId, { optionIndexes? }) → CompareTable

  • 输入：该消息中指定（默认全部 open）的选项，加 5.2 第 3、4 级上下文。
  • 任务要点：对每个选项在 6 个维度上各写一句话（≤ 40 字）：核心冲突、人物影响、节奏、风险、后续展开、与已有设定的契合度；并给出契合度等级。不推荐、不替作者选择。
{ "columns": [ { "optionIndex": number,
                 "cells": { "conflict": string, "characters": string, "pacing": string,
                            "risks": string, "followups": string, "fit": string },
                 "fit": "high" | "medium" | "low" } ] }

dimensions 由本地固定填写，不由模型生成。

6.5 splitForAdoption(messageId, optionIndex) → AdoptItem[]

  • 输入：该选项全文、作者与 AI 的最近 2 轮对话、作品现有条目的名称与类型列表（只给名称，不给字段）。
  • 任务要点：把选项拆成档案条目，最多 6 项；每项只填 6.0 中该类型的字段；只写选项里明确的内容，不补充新设定；与现有条目同名的用现有名称。
{ "items": [ { "type": "character" | "world" | "place" | "faction" | "rule" | "foreshadow",
               "name": string,       // ≤ 30 字
               "summary": string,    // ≤ 60 字
               "facts": [ { "field": string, "value": string } ] } ] }  // value ≤ 300 字

本地匹配（S10c 展示前）：同作品同类型下名称或别名完全相同 → action: 'update'，填 targetEntryId，每个字段的 before 取该条目当前值；否则 action: 'create'。field 不在 6.0 中的项丢弃。

6.6 describe({ chapterId, range, types, style, extra, referenceIds, count })

  • 执行：发起 count（1–3）个独立的流式请求，同时进行；"再写一版"再发 1 个。每个请求在用户消息末尾加"这是第 N 个版本，写法与其他版本不同"。
  • 上下文：5.2 第 1–4、7 级；第 4 级只包含 referenceIds（S08 中作者保留和添加的条目）。
  • 任务要点：只写这一段描写，不推进剧情、不新增人物、不改变已确认设定；视角、人称、时态与前后文一致；直接输出可放进正文的文字，不加标题、引号、解释或 Markdown。插入模式默认 150–400 字；改写模式约为原文的 0.8–1.5 倍。类型、风格、补充要求原样写入提示。
  • 后处理：去掉首尾空白和成对的外层引号；按 G02 4.6 规范化段落。

6.7 quickEdit({ chapterId, range, op, count })

与 describe 相同的执行方式和后处理，上下文为 5.2 第 1–4 级（第 4 级为选区及前后文中提到的条目）。各操作的提示要点（长度目标写进提示词，不做硬截断）：

op界面名要点长度目标
rewrite改写换一种写法表达同样的内容原文的 0.8–1.2 倍
expand扩写增加动作、感官和心理细节，不新增情节1.5–2 倍
shorten缩写保留关键信息和语气0.5–0.7 倍
polish润色修正语病、调整节奏和用词，保持原意和风格0.8–1.2 倍
detail补细节在原文基础上补充环境或外貌等具体细节约 1.3 倍

6.8 completeEntry(entryId, fields[], extra?)

  • 上下文：该条目全部字段（含状态）、与它有关系的条目的名称与一行摘要、5.2 第 3 级、最近 3 章摘要。
  • 任务要点：只为指定字段写建议；与已确认设定保持一致；已有值的字段给出修改建议并说明理由。
{ "facts": [ { "field": string, "value": string, "reason": string } ] }   // value ≤ 300 字，reason ≤ 40 字

写入：entries.proposeFacts(entryId, facts, { kind: 'ai_complete', ref: null })。不在请求字段中的结果丢弃。

6.9 summarizeChapter(chapterId)

输入本章正文和作品信息。要求：60–120 字，一段，概括本章发生的主要事件和变化，不评价、不剧透后文，不用 Markdown。超长时截断到 150 字。写入 chapters.summary。

6.10 extractMemory(chapterId)

  • 输入：首次定稿为本章全文；再次定稿时只给与上次定稿版本相比新增或改动的段落（versions.diff），并附前后各一段作为语境。另附本章及前后文中提到的条目（已确认、正文已建立的字段，带生效章节）和最近 3 章摘要。
  • 任务要点：只提取正文中明确发生或明确交代的事实，不推测；每条必须附正文原句（逐字摘录，≤ 80 字）；与档案已有内容一致的不提取；最多 30 条。
  • 分段：输入正文超过 12,000 字时，按段落边界切成每段 ≤ 12,000 字依次请求，合并结果，按"目标 + 字段 + 新值"去重。
{ "changes": [ { "kind": "add" | "update" | "retire",
                 "targetType": "character" | "world" | "place" | "faction" | "rule" | "foreshadow" | "relation",
                 "targetName": string,
                 "field": string | null,      // 6.0 中的键；relation 时为关系类型
                 "before": string | null,
                 "after": string,             // ≤ 200 字
                 "evidence": string,          // 正文原句
                 "confidence": "high" | "medium" | "low" } ] }

后处理：按名称和别名匹配 targetEntryId（匹配不到且 kind 为 update / retire 时改为 add）；在规范化后的定稿正文中逐字查找 evidence 得到 evidenceOffset，找不到时为 null 且置信度降一级；然后调用 proposals.createFromExtraction。

6.11 detectConflicts(chapterId)

  • 输入：本章正文（同 6.10 的分段规则）；本章及前后文提到的条目的已确认、正文已建立字段（带生效章节和出处）；最近 3 章摘要。已标为"有意为之"的冲突以"作者已确认不是问题"列出，避免重复报告。
  • 任务要点：只报告正文与档案之间、或正文前后之间明确的矛盾（年龄、时间、地点、能力限制、人物关系、物品归属、事件顺序）；说明为什么矛盾；给出最多 3 条修改建议，同时提醒"如果是有意的误导或伏笔，可以保留"；最多 10 条。
{ "conflicts": [ { "type": "setting" | "character" | "timeline" | "item" | "relation",
                   "severity": "high" | "medium" | "low",
                   "a": { "source": string, "quote": string },   // 本章正文
                   "b": { "source": string, "quote": string },   // 档案或前文
                   "explanation": string,                        // ≤ 120 字
                   "suggestions": string[] } ] }                 // ≤ 3 条，每条 ≤ 60 字

后处理：解析 b.source 对应的条目或章节，得到 entryId 与引用；调用 conflicts.createFromDetection（去重和"有意为之"过滤在 G02 完成）。

7. 通用系统提示要点

  1. 你是小说创作顾问，作者决定剧情；你提供问题、选项和局部文本。
  2. 只完成要求的范围：描写不推进剧情，不新增人物，不改变已确认设定。
  3. 已确认和正文已建立的设定是约束；标为"提议"或"未确认"的内容只作参考。
  4. 区分来自正文或设定的事实、你的推断和你的建议。
  5. 借鉴其他作品时只分析叙事手法，不复制具体人物、情节或表达。
  6. 用简体中文，遵循作品的文风偏好。

提示词放在 src/ai/prompts/，每个任务一个文件，带版本号；版本号随用量记录保存，便于以后对比效果。

8. 错误

判定优先级：本地取消/deadline → HTTP 与已识别服务商 code（quota 优先于 rate_limit）→ 成功响应/流结构校验。未列出的 4xx 归 AI_BAD_REQUEST，其他 5xx 归 AI_SERVER；不以未知服务商原文替代安全文案。适配器把 HTTP 状态和服务商错误体映射为以下错误码，写入 AiErrorInfo（G02 第 2 节）。文案沿用产品设计 6.9；技术详情在 D05 错误详情中查看。

错误码判定界面文案自动重试界面操作
AI_NETWORK无网络、DNS、TLS 证书失败、连接被拒绝连不上 {域名}，请检查地址或网络。否重试、编辑服务
AI_TIMEOUT首字节 60 秒或逻辑请求硬期限耗尽（测试/列表总计 20 秒）{域名} 没有响应，请稍后重试或检查网络。后台任务 1 次重试

9. 重试

  • 只对 AI_RATE_LIMIT、AI_SERVER（以及后台任务的 AI_TIMEOUT）自动重试，前台和后台都适用，最多 2 次；后台 AI_TIMEOUT 最多 1 次。测试与列表优先遵守第 6.1–2 节更严格的规则。
  • 等待时间：响应头 retry-after-ms（有效毫秒）优先，其次 retry-after（秒或 HTTP-date，负值按 0；非法值忽略），前台最多等 20 秒、后台最多等 60 秒，超过上限视为失败；没有响应头时等 1 秒、3 秒。响应头 x-should-retry: false 时不重试。
  • 前台重试期间，候选卡或消息显示"服务繁忙，正在重试（1/2）"，可点"停止"。
  • 流式请求只有在还没收到任何文字时才自动重试；已经有文字时保留错误原因并按中断交互处理，由作者选择"继续生成"。
  • 业务任务的参数降级、格式修复、网络重试均计入 G04 总物理请求次数；单请求最多 3 次，多候选/分块共用 N+2 上限，原有分支重试次数只是局部上限。测试仍以 6.1 为准。
  • 后台任务自动重试用完后为 failed，由作者在 S05b 手动重试（G02 第 6 节）。

10. 取消

每个请求绑定一个可中止句柄（流式为 xhr.abort()，非流式为 AbortController）。触发中止的情况：

情况处理
作者点"停止"已生成文字保留。AI 伙伴消息为 stopped（conversations.stop）；描写候选标记"已停止"，仍可插入
关闭描写候选弹窗中止全部候选请求，候选丢弃
离开作品（回到书架）中止该作品的 AI 伙伴生成，保存为 stopped。切换作品内标签不中止
S02/S02a 关闭、连接字段变化或保存中止该页面测试/列表并递增请求代次，丢弃迟到结果；S15a 离页继续测试但不弹 toast，删除服务则中止
App 进入后台前台请求不主动中止（系统可能挂起网络，回到前台后按超时规则判断）；后台任务中止并回到 queued
重新定稿、删除章节或作品重新定稿/删除章节按 G02 取消任务；作品删除只阻止执行和结果写入，不由 works.remove 修改任务表

11. 用量与日志

  • 记录：全部物理 AI 尝试按 G04 §9写本地账本，包含重发、失败、取消与连接测试；未知用量保留 null。伙伴消息继续保存 usage 摘要并在 S10e 查看，汇总只以 attempts 账本计一次。
  • 日志：仅记录本地 requestId、任务名、协议、归一错误码、HTTP 状态、耗时、长度；不记录请求/响应体、headers、Key/掩码/哈希、用户正文或完整原始异常。发布版只记录同样白名单内的错误信息，原生传输日志同样受限。
  • 脱敏边界：服务商 error.message 可回显凭据/提示词，不可直接放进 AppError、AiErrorInfo、lastTest、toast 或 D05。归一器只输出本地模板与已识别错误类别；providerMessage 只保留本地映射的安全诊断，未知原文为 null。requestId 仅保留受限长度/字符的服务端标识，含凭据内容或来源不明则 null；其余响应标量（含 responseModel）同样校验与脱敏，不能把对象 stringify。不得以仅替换 sk- 前缀作为安全保证。
  • 隐私：请求只发往该服务自己的地址，Key 仅在鉴权头中；按 2.1 在原生层禁止跳转转发。D05 只接收脱敏数据，复制不另拼原始错误。
