G04更少的无效调用，更好的写作结果

1. 优化什么

目标：在事实可靠、作者意图不变的前提下，降低一次可采纳结果的总费用。

不能只比较单次价格或压低输出上限。低质量回答带来的重生成、修复和重复输入也要计入；推理 token、缓存写入和取消前已发生的生成也可能收费。各服务的真实价格未知时，只报告 token 与请求次数，不显示虚假的金额。

本地解决检索、名称匹配、去重、diff、Schema 校验、格式规范化无需模型。
只发送相关内容事实按章节生效，来源可追溯，作者选中的参考不会被悄悄丢掉。
每次操作有边界统一请求次数、输入/输出预算、取消和期限；所有重发共用预算。
结果可验证证据校验、人工采纳、版本绑定与效果评测；不默认增加模型评审调用。

本轮不引入业务服务器、LangGraph、多 Agent 互评、远程向量库或自动联网搜素材。现有规模先用 SQLite、FTS5 和纯函数；检索召回不足有评测证据后，再通过 Retriever 扩展端上向量检索。

3. 最小可扩展实现

页面 → features AI 门面 → TaskPolicy + ContextPlan
                        → RequestBudget / AttemptLedger
                        → 已有 Provider → 已有 Native Transport
                        → 本地校验 → features 受限写入

ai/tasks/       任务输入、提示词版本、预算、输出校验；不持有任意 DB commit
ai/context/     纯组装器、检索端口、token 估算、不可变发送计划
ai/runtime/     尝试调度、去重、预算预留、取消、期限
features/      快照读取、预算/用量落库、结果的业务事务、提交后事件
ai/providers/  协议参数与 usage 映射；复用现有实现
ai/evals/      离线 fixtures、质量约束和可选实测脚本

这些是职责边界，不要求每项建一个框架或类。B 阶段先为 describe/quickEdit 落实最小实现，遇到第二个实际调用方再抽共用代码。任务定义只能返回已验证结果，由 features 完成带版本检查的事务；避免把通用 commit(out, tx) 暴露给任意 AI 任务而绕过正式事实边界。

4. 本地检索与上下文质量

  1. 先按任务划定范围：当前选区/局部段落、作者手选引用、截至当前章的设定、相关摘要。书的所有章节、全部字段和完整聊天不默认一起发送。
  2. 本地检索：作者指定条目 → 名称/别名最长匹配 → FTS5 trigram 补召回 → 必要的一跳关系。少于三个字用转义后的 LIKE；带 workId、删除状态和事实有效区间过滤。排序按指定、精确命中、相关性、稳定 ID，避免随机顺序破坏可重复性。
  3. 范围优先：describe 只允许 S08 最终保留的 referenceIds，不能用 FTS 把作者移除的条目偷偷加回。FTS/关系扩展用于其他允许的任务或作为作者可选参考，preview 必须列出。手选条目只带相关有效字段，不自动带整个历史。
  4. 保护必要事实：系统约束、直接输入、用户明确要求、手选参考中的相关有效事实及必要冲突说明不可静默删除；最近 2 轮对话在伙伴任务中也作为最低上下文。过大时先扩至服务上限，仍不够则提示缩小范围。自动检索的低相关信息可按 G03 优先级裁剪；不能把文风说明保留下来却删掉不可违反的设定。
  5. 区分事实：已确认/正文已建立、冲突、未确认提议分别标识。历史事实按章节顺序求值，禁止把未来能力或关系带到早期章节；废弃/回收站内容不参与。
  6. 保持原文：摘要供导航和语境，不能代替记忆提取/冲突判断的证据。正文中的「忽略设定」等文字属于素材，不可作为应用指令。输出字段/来源 ID 均按同作品白名单校验。
  7. 先选再排序：相关性决定哪些块入选，稳定顺序决定序列化顺序。稳定系统规则/任务提示置前，动态选区、当前问题及候选风格差异置后；不为了命中缓存增加无关内容或改变指令优先级。

预览与发送：二者使用同一份不可变 ContextPlan。若预览后正文、选区、引用或服务变化，发送前重新生成并刷新预览；已开始的请求继续使用捕获的快照，不能半途换正文。插入时重新校验编辑器会话/来源版本，过期候选须作者重新定位，不按旧偏移覆盖。

token：优先使用可在 RN 离线运行且与模型匹配的 tokenizer；不为计数多发模型请求。无 tokenizer 时先用 G03 字符公式 × 1.3 的估算余量，再用实际 usage 校准模型/协议倍率；这是启发式，不是保证。已知上下文窗时校验输入估算 + 最大输出 + 协议余量 ≤ 窗口；未知不假设 100k 可用。选择完整事实/段落块裁剪，不把事实截成改变含义的半句。

6. 所有重发共用预算

一次作者操作或一个后台 job 是 logicalRequest。令 N 为预先计划的物理请求数：单次文本 N=1，多候选 N=count，长文 job N=分块数。每个逻辑请求最多 N+2 次 POST，额外 2 次在所有子请求间共享；正常只发 N 次，不能为了用完额度主动重试。每个子请求本身最多 3 次。参数降级、网络重试、格式修复均在此上限内，且不得突破总输出预留和期限。

一次定稿会产生三个 job，必须再挂到同一个持久化父操作预算：N 为三类任务计划调用数之和，额外尝试合计最多 2 次，子 job 额度不能绕过父额度。预览和授权展示整个定稿操作的预计消耗；摘要/提取生成后若依赖变化导致追加工作，先重新检查父预算，不因进入下一步重置额度。

  1. 发送前以短事务预留一个 attempt 的输入估算/最大输出及可选金额；并发候选共享原子预算，不各自认为还有两次。网络与 Key 读取在事务外。
  2. 只有 G03 已允许的临时错误、明确不支持参数或 Schema 失败才可重发；取消/配额不足/鉴权错误/已输出正文不自动重发。格式修复最多一次，带紧凑校验错误和必要上下文，不发送整个日志。
  3. 每次重发输出上限不超过首次允许值；长度截断保留已生成内容，结构化半截数据不入业务库。提高上限或换模型必须由作者明确操作，形成新预算。
  4. 普通前台仍共享 5 分钟硬期限；分块作业每块最多 5 分钟、整个 job 最多 min(5×N, 30) 分钟，重发不重置期限。计划超过 6 块时先暂停展示范围和预计消耗，由作者拆分范围或选择后续批次，不静默启动大额作业。
  5. 多个分块只有全部完成并通过校验，才能把该 job 标为 done；中断保留已验证的分块派生结果，明确标记「未完成」，不得声称完整审查无冲突。

业务层可设置每次操作/每日的 token 或可选金额软上限；无可靠价格时以请求数和 token 预留约束，不能承诺精确账单封顶。余额预留只能限制本 App 的请求，不能管住同 Key 在其他工具的支出。达到上限暂停，作者可取消或明确提高，不能自动切廉价服务继续花费。

新业务状态：AI_BUDGET_EXCEEDED（可调整范围/额度）、AI_RESULT_STALE（重新定位或重生成）；job 暂停原因增加 budget / interrupted / legacy_input。未知是否已计费的 attempt 保留为 unknown，并继续占用其保守预留直到作者处理；不将取消、无 usage 的失败或重启视为免费。

增量定稿分析绑定新旧 finalizedVersionId；按段落 diff 定位变更，携带邻段与相关事实。首次无基线则全章删除会使旧证据、提案、冲突的派生依赖失效；正式事实不能自动删除，只进入待审核。冲突检测不能仅看改动句而忽略它影响的其他段落

本地派生缓存是可重建数据，作用域限本作品，使用正文/依赖的本地内容指纹，不含 Key 或其指纹；不导出缓存、不记录内容哈希到遥测。存储限制初值 20 MiB，LRU 淘汰，删除作品时清理；不足时跳过缓存写入，不让缓存失败阻塞正文保存。创作候选仍按现有设计只保留页面内存。

Prompt caching 的实现边界：第一阶段只做稳定前缀排序，不改已验证的协议参数。后续为有已核实文档支持的 service/model 增加可选 cache policy，封装在 provider；未知或兼容网关默认不发厂商专有字段。现有 OpenAI 顶层 instructions 不能直接放显式断点；若启用新的 developer content block 映射，须单独更新 G03 的协议契约与合成测试，不由业务任务拼厂商参数。Anthropic 的缓存字段与计费口径必须另行核对官方文档，不能照搬 OpenAI。能力探测不得额外触发收费请求，正常调用明确不支持时的降级也消耗共享尝试额度。

按同一前缀 S token、预计 N 次使用评估：启用显式缓存的输入费用约为 S×[写入价+(N−1)×读取价]，不缓存约为 S×N×普通输入价；两者还要加动态输入和输出费用。一次性、很短或经常变动的前缀可能没有收益。此为估算模型，实际以服务返回 usage 和账单为准。

8. 版本、崩溃恢复与正式事实边界

后台 job 必须新增 sourceVersionId、inputFingerprint、dependencyRevision、serviceId/serviceRevision、policyVersion 与 executionToken；网络返回后先核对任务仍拥有执行权、作品/章节未删除、版本和依赖仍有效，再在同一事务写业务结果并完成 job，提交后发事件。作品删除继续遵守 works.remove 不修改任务表的既有决定，由执行/提交校验拒绝结果。

以任务类型 + 来源版本 + 依赖指纹做活跃任务去重，业务结果写入也用逻辑任务 ID 唯一约束避免重复提案。重新定稿使旧执行 token 失效；过时结果可留历史诊断但不得应用。服务修改/删除后，不用旧配置复活任务，不默默改用新默认。

无法在普通 HTTP 上保证服务端恰好执行一次。若发送后进程退出、网络断开且没有可靠终态，恢复为「中断，可能已计费」，等作者选择重试；不能把 running 一律重置再自动发送。仅有本地预算预留、可证明还未发出的请求可释放预留并重排。旧版排队任务缺少输入版本时进入 legacy_input，作者重新确认定稿后才建立新任务。

提取结果先校验来源属于本作品、原句能在捕获版本定位。找不到证据的项目显示待核实并降低可信度，不自动升级为正式事实；歧义同名不自动合并。局部跨章事实更新、关系变化和纯删除均须保留旧历史，正式设定的变化最终由作者确认。

9. 用量账本与可理解的界面

新增 ai_requests（逻辑操作/预算/用户采纳结果）和 ai_attempts（每次物理 POST），请求发出前登记，结束时幂等结算。attempt 只记录：本地 ID、关联 work/job/message、任务/策略版本、服务 ID/revision、模型、开始结束时间、归一状态、输入/输出估算与实际用量、缓存/推理可空明细、价格快照/币种、估算或报告的费用状态。没有正文、提示词、Key、完整 URL/headers 或原始异常。

模型列表 GET 不当作生成 token；连接测试 POST 也记账，但不会混入写作采纳率。所有流用量采用最后累计快照，不累加每个事件。OpenAI cached/reasoning 等明细可能已包含于 input/output 总数；Anthropic 缓存 token 与普通 input 的口径不同，provider 必须明确归一为互不重叠的收费桶并保留未知值，不能直接相加猜总数。缺少细分时显示总量并把精确费用留空。重试失败的已报告用量也保留。

价格由用户/已核实的服务定价填写，按 service + model + currency + 生效日期保存快照；不要把官方价格套到自定义中转。不同币种分别汇总，不默默换汇。金额标为「估算」或「服务报告用量计算」，不冒充账单；未知 usage 显示「未返回，可能已计费」，不是 0。

  • S08/S09：继续使用简洁的「生成 1 版 / 再写一版」，发送前展示参考范围和预计消耗；停止后保留文字，价格未知显示 token/请求数。
  • S10a：展示实际入选来源、状态和被省略原因；用户选中的参考超额时给调整范围选项。
  • S05b：展示整个作业的块数、完成块数、尝试次数、预算及暂停原因；「中断后重试可能再次计费」仅在实际发生时提示。
  • S15：轻量「本机 AI 用量」和可选写作/整理/校对服务选择，默认沿用默认服务；不把 provider、Schema 或内部类名放进主创作流程。

10. 用效果评测决定是否真的省钱

每项优化单独对比原始策略和新策略，固定输入快照、服务/模型、输出条件与预算；先用小型合成中文样本，再在明确授权下做真实模型评测。不得以 347 个现有工程测试通过宣称文风、推理或成本收益已验证。

11. 实施顺序与设计同步

  1. A：先落地档案、关系、FTS 与按章有效事实；为检索提供真实数据基础。
  2. B：两种写作任务 + D01 + ContextPlan + 预算/账本 + 候选插入；补迁移与规范默认值，费用未知时 token 模式也能完整使用。
  3. C：伙伴、结构化验证、对比与采纳；新增功能复用已验证的预算机制，不再各建重试循环。
  4. D：定稿快照和队列恢复先于 runner；再做摘要/提取/冲突和审核 UI。
  5. E：补全/路由/用量 UI 与剩余 MVP；显式厂商缓存按实际支持情况单独启用。后续向量检索、长会话语义摘要、合并多种分析为一次请求需各自证明费用和质量收益，当前不做。

每阶段将 G04 变化同步到 G02 精确类型/迁移、G03 对应规则、涉及 S/D 页面与测试。只加需要的迁移，不修改已经运行过的 0001/0002。保留旧数据、服务与显式用户偏好。结果缓存、路由策略和新预算按独立模块可关闭；关掉优化不应破坏已保存正文或正式档案。
